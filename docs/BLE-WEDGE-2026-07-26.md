# The BLE wedge — everything times out while the car is still talking

**Status:** root cause is a strong, evidence-backed hypothesis. NOT yet proven. Do the
instrumentation in §5 before writing the fix in §6.

**Symptoms Ivan reports:** PE-4 fails when the car is UNLOCKED and passes when it is LOCKED;
sending locations to the car sometimes hangs and needs an app restart; occasional "all BLE
messages ignored" until relaunch.

---

## 1. What the log actually shows

The decisive block, 2026-07-26 17:17–17:18 (car unlocked, doors open):

```
17:17:48.901  exchange 152B  ok    193ms
17:17:52.335  push vcsec  {"locked":false}
17:17:54.942  exchange 248B  FAIL  6001ms  "stale frame: no matching response"
17:17:56.833  push vcsec  {"locked":false, closures:{frontDriverDoor:open, ...}}   <-- car talking
17:18:00.603  exchange 152B  FAIL  4009ms
17:18:01.093  push vcsec                                                           <-- car talking
17:18:01.305  push vcsec                                                           <-- car talking
17:18:04.774  exchange 152B  FAIL  4168ms
17:18:08.976  exchange 152B  FAIL  4098ms
   ... every SessionInfoRequest times out from here ...
```

**The car is pushing to us throughout.** VCSEC frames arrive at :56, :01 and :01 while every one
of our exchanges times out with *no matching response*.

So this is **not** "the car stopped answering". The link is up in both directions. Our exchanges
simply never see a frame that matches their request.

An identical episode at 15:04–15:05 lasted ~78s and self-recovered; another at 17:15. The 17:13
PE-4 run (car unlocked) shows the milder form: one command at 2189ms among otherwise-normal
270-300ms ones. Locked, the same run is clean (worst 331ms).

## 2. Why "unlocked" matters

Unlocked and doors open ⇒ **a lot** of unsolicited VCSEC push traffic (presence, per-door closure
changes). Locked and idle ⇒ almost none. The correlation Ivan noticed is therefore
"much more inbound push traffic", not "unlocked" per se.

## 3. The hypothesis: the RX reassembly buffer desyncs and cannot recover

`BleReassembler` (`src/ble/bleFraming.ts`) is a SINGLE byte stream:

```ts
this.buf = concatBytes(this.buf, bytes);
const msgLength = this.buf[0] * 256 + this.buf[1];
if (msgLength > MAX_BLE_MESSAGE_SIZE) { this.buf = new Uint8Array(0); break; }  // corrupt-prefix guard
if (this.buf.length < 2 + msgLength) break;
complete.push(this.buf.slice(2, 2 + msgLength));
```

Two escape hatches exist, and the failure mode slips between them:

1. **Corrupt-prefix drop** fires only when the declared length exceeds `MAX_BLE_MESSAGE_SIZE`
   (1024). A desynced buffer usually reads a *plausible* length from the middle of a frame, emits
   garbage, and stays desynced — silently, forever.

2. **Stale-gap flush** (`RX_STALE_GAP_MS = 1000`) clears a partial buffer after 1s of silence.
   **But the car is pushing roughly every second when doors are open**, so the gap never opens
   and the flush NEVER FIRES. The condition that causes the desync is the same condition that
   prevents recovery.

That predicts exactly what we see: a wedge that begins under heavy push traffic, persists while
that traffic continues, self-heals when the car finally goes quiet (15:04 recovered after ~78s),
and is always cleared by an app restart (fresh buffer).

It also explains **"sending locations hangs"**: a nav payload is large, so more chunks, so a wider
window for an interleaved push to land mid-message.

## 4. Why our recent fixes did not help — and one that may hurt

- Scoped eviction, priority queue and the deaf-window fix all address *contention*. This is
  **corruption**, and none of them touch it.
- `BACKGROUND_READ_TIMEOUT_MS = 1200` may make it WORSE: giving up sooner means the car's reply
  arrives after we stopped waiting, and a late reply is more interleaving. **Consider reverting
  to the normal timeout if §5 confirms the desync.**

## 5. Instrument FIRST — do not fix on this hypothesis alone

The whole point of today was that unmeasured mechanisms were wrong three times. Add, in
`BleReassembler`:

- a counter of frames emitted whose **first byte cannot begin a valid RoutableMessage** (field 6
  or 7 ⇒ `0x32`/`0x3a`), which is the cheap desync tell;
- the buffer's residual length whenever an exchange times out;
- log every inbound frame's `requestUuid` during a wedge, next to the uuid we are waiting for.

**The one measurement that settles it:** during a wedge, are inbound frames (a) well-formed but
for an OLD uuid — a correlation problem — or (b) not well-formed at all — a framing problem? §3
predicts (b). Extend PE-1's capture, which already records raw frames, and read them.

## 6. Candidate fixes, once confirmed

1. **Bound the desync.** If N consecutive emitted frames fail to parse as a RoutableMessage, reset
   the buffer. Cheap, targeted, no protocol change.
2. **Resync on a length that does not lead anywhere.** After slicing a message, sanity-check the
   next 2 bytes; if the implied length is impossible, drop one byte and retry rather than trusting
   the stream.
3. **Flush on exchange start.** `exchange()` already clears `this.inbox`; it should arguably clear
   the reassembler too, since any partial message at that moment cannot belong to the request we
   are about to send.
4. **Do not shorten timeouts until this is fixed** — see §4.

## 6b. UPDATE 2026-07-26 18:37 — there are TWO failures here, not one

The repro ran (car unlocked, driver door open) and produced the outlier — one command at 2131ms
among otherwise-normal 270-331ms. **But the rx desync counters never engaged, because no
stale-frame timeout fired at all.** So this is NOT the wedge. Keep them apart:

| | the 2131ms outlier | the WEDGE |
|---|---|---|
| symptom | one slow command | EVERY exchange times out, 60-90s |
| trigger | a LINK-scoped eviction + cold handshake | unknown |
| recovery | immediate | needs the car to go quiet, or an app restart |
| rx counters | never fired (no timeout) | not yet observed |

The outlier's cause is visible in the log:

```
18:37:33.063  evicted all sessions ... dropped domains: 2,3 · trigger=2   <- LINK-scoped
18:37:33.172  openSession                     2ms
18:37:33.245  exchange 152B (session info)   73ms                        <- cold handshake
```

**The link was not dead.** It re-opened in 2ms and exchanged at 73ms immediately afterwards. Yet
something tore down BOTH domains. `evictScopeFor` only narrowed the `timeout` case; the
transport-dead and `unreachable` paths still evict everything, and the log could not say which of
them fired.

Fixed that: every `evictSession` call site now passes a `reason`, so the next occurrence names its
own cause (`transport-dead` / `unreachable` / `timeout` / `cached-session-transport-dead` /
`cold-start-stale-session` / `session-refresh-failed`).

**The question for the next run:** if the reason is `transport-dead` or `unreachable` while the
link demonstrably works two milliseconds later, then that classifier is wrong and the fix is there
— not in the reassembler. The wedge itself remains unreproduced under the current build.

## 6c. UPDATE 2026-07-26 19:00 — the evidence has moved AWAY from the framing hypothesis

With the eviction reasons finally shipping, every link-scoped eviction in the 18:58-19:02 window
reads:

```
evicted all sessions ... dropped domains: 2,3 · trigger=2 · reason=unreachable
```

`classifyTransportError` returns `'unreachable'` as its **catch-all** for any error without a
recognised kind — and a stale frame has none. So a stale frame that exhausts its retries was being
called unreachable and taking down BOTH domains, while the link re-opened 2 ms later and exchanged
at 73 ms. It was never unreachable. Fixed: a stale frame now evicts its own domain only, with
`reason=stale-frame-exhausted`.

**And the stale frame's own text points at the correlation branch, not framing:**

> `decrypt failed against this request's AAD (counter=2026, requestHash mismatch — channel had a
> buffered response to a different request)`

That is a response to an EARLIER request arriving while we wait for a later one — well-formed
frames, wrong request. §5 posed the question as (a) correlation vs (b) framing and §3 predicted
(b). **The evidence so far says (a).** The reassembler desync is not ruled out — the rx counters
have still never fired, because no stale-frame TIMEOUT has occurred since they shipped — but it is
no longer the leading candidate.

Revised leading theory: a request times out, we stop waiting, the car answers late, and that late
answer is then matched against the NEXT request — which fails its AAD check, is called a stale
frame, exhausts retries, and (until this fix) tore down the link. A one-behind channel.

If that is right, the fix is to make an abandoned request's late reply identifiable and discarded
rather than allowed to confuse the next exchange — and `BACKGROUND_READ_TIMEOUT_MS = 1200` makes
this MORE likely, not less, since giving up sooner guarantees the reply lands after we stopped
waiting. §4 flagged that as a risk; treat it as promoted.

## 6d. UPDATE 2026-07-27 04:41 — PE-4's wedge is largely a PROBE ARTIFACT

The correlator fix (routing_address is per-session, so a late reply satisfied the next request)
shipped and the app relaunched with it at 21:17:31. PE-4 then degraded catastrophically:

```
04:38:14  SAFE       quiet  90/120     loaded   298/328
04:38:28  SAFE       quiet 120/150     loaded   272/420
04:38:56-04:39:45  EIGHT passive-entry auths, all GRANTED
04:39:15  DO NOT     quiet 119/121     loaded   542/10918
04:40:36  DEGRADED   quiet 388/417     loaded 12447/25003
04:40:55  DEGRADED   quiet 6870/12721  loaded  6306/25007
04:41:08  DEGRADED   quiet 7020/24989  loaded   300/12389
```

But the app itself was HEALTHY throughout:

```
04:41:13  poll focused  170ms
04:41:15  poll focused  173ms
04:41:17  poll focused  180ms
```

and exactly ONE app-side exchange failed in the whole window. The probe's hold on background
polling also worked — zero `poll` rows between 04:40:36 and 04:41:10 — so the app was not competing
for the link. **The link was fine. Only the probe's own gateway was wedged.**

### The mechanism this points at

carlink.tsx's `makeGateway()` opens its OWN session: its own routingAddress, its own counter. The
app has another. Both authenticate with the SAME device key against the SAME VIN, and Tesla's
counter is monotonic PER KEY — so the two sessions share a counter space they each believe they own.

Between probe runs the app polls (~every 1.8s) and passive entry answers challenges, each
advancing that counter. The probe's cached session falls further and further behind, and its
commands are rejected or ignored — which is exactly the PROGRESSIVE degradation above, and why it
accelerated right after eight passive-entry auths.

This is the **two-gateway hazard already on the roadmap as a known, unfixed item**. It is not new,
and the correlator fix neither caused nor addresses it.

### What this does NOT settle

The ORIGINAL symptom — sending a location hangs in normal use until the app is restarted — happens
in the APP, which has only one gateway. So two-gateway cannot explain that one.

The single-app analogue is worth examining next: the passive-entry responder seals answers OUTSIDE
the gateway's queue, consuming the same per-key counter while a command may be mid-flight between
its own seal and its write. That is the same counter-allocation race, one layer down, and it fits
"wedges correlate with the car challenging us".

**So: fix the two gateways first** (it makes every future PE-4 number trustworthy), then re-examine
counter allocation between the responder and the command path. Do not run PE-4 as evidence about
the app until the first is done — it has been measuring its own artifact.

## 6e. UPDATE 2026-07-27 05:29 — the shared queue holds, tested by accident

Four PE-4 runs after `queue` was defaulted to `sharedSessionQueue`. Ivan pressed
the button twice in a row, so runs 3 and 4 started **1.3 seconds apart** and
overlapped — two probe gateways issuing commands concurrently, which is EXACTLY
the two-writer scenario that produced 25-second commands at 04:40.

```
05:29:18  SAFE      quiet 121/151  loaded 301/359
05:29:23  SAFE      quiet 120/121  loaded 271/300
05:29:29  SAFE      quiet 120/242  loaded 215/303    <- overlapping
05:29:30  DEGRADED  quiet 212/450  loaded 300/419    <- overlapping
```

Zero failed exchanges. Zero evictions.

```
CONCURRENT probes, BEFORE the shared queue (04:40:55):  WORST 25007ms
CONCURRENT probes, AFTER  the shared queue (05:29:30):  WORST   419ms
```

Two writers now SERIALIZE instead of racing the counter: slower under contention
(215-419ms rather than 271-303ms), which is the expected cost, and correct.

The baseline gate also earned itself. Run 4's quiet phase hit 450ms — because
run 3 was still going — and it reported BASELINE DEGRADED rather than blaming the
focused read. That is exactly the misattribution it was added to prevent, caught
on its first real occurrence.

**Caveat:** one session, short runs, and an accidental rather than designed A/B.
It is strong evidence, not proof — but it is a direct before/after on the same
scenario.

## 7. Repro

`PE-4 command latency` with the car **unlocked and a door open** fails; the same run with the car
locked passes. That is the cheapest reproduction we have, and it needs no handle pull.

## 8. What is NOT affected

Passive entry does not go through this path for its *answer* — it writes directly under the write
lock and measured 1-2ms even while 4 of 5 background reads were failing (PE-1, 16:54). But it
DOES depend on the reassembler to receive the challenge, so a desynced buffer could still hide a
challenge. **Treat "unlock is safe" as unproven under wedge conditions.**
