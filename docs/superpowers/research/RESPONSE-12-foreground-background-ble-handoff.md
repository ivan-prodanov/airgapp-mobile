# RE RESPONSE #12 — the foreground↔background BLE-ownership handoff: use (b), and it's *forced*

**Answers:** `REQUEST-12-foreground-background-ble-handoff.md` (Q1–Q3 + the model + the bridge surface).
**Method:** static RE of the **real official iOS Mach-O** (`TeslaV4` 4.57.5, arm64, extracted from the IPA) + its Hermes JS bundle + Android jadx + airgapp, and the CoreBluetooth platform semantics. **4 trace finders → 2 adversarial-refutation verifiers → completeness critic**, plus an independent re-count of airgapp's central-construction sites.
**Verdicts:** T1 ownership **HIGH**, T2 restoration-seam **HIGH**, T3 RN-opens-central **HIGH**, T4 CB-fact+bridge **HIGH**; V1 native-always-on **SUPPORTED/HIGH** (4 vectors failed), V2 no-cross-central-handoff **SUPPORTED/HIGH** (3 vectors failed).

## TL;DR — model (b), and CoreBluetooth *forces* it

**Adopt (b): a native component owns the ONE connection-holding `CBCentralManager` full-time (foreground + background, via CB State Restoration), and the JS command path submits BLE bytes to it through a bridge. Reject (a) lifecycle handoff.** This is not just what the official app does — it's the only architecture CoreBluetooth permits:

- **The official app IS (b), proven at disassembly level.** One native per-VIN central (`BLEVehicle._centralManager`) holds the car link and multiplexes commands + passive-entry challenges; the Hermes JS bundle has **zero** `ble-plx`/`BleManager`/`CBCentralManager` tokens and reaches BLE only through named native bridge selectors; `applicationDidEnterBackground` does **zero** BLE teardown (the app *persists* the central, never hands it off).
- **(a) is forced to be unsafe.** A `CBPeripheral` is bound to the `CBCentralManager` that vended it — there is **no in-process API to transfer or share a live connection** (empty symbol search confirms the app carries none), and no atomic swap primitive. So "handoff" is always *disconnect-A + fresh-connect-B*, which is forced into **gap-XOR-overlap**: cancel-A-first → a **gap** (a background `0213` challenge lands unanswered → passive entry dead); connect-B-first → an **overlap** (two centrals on one peripheral → your proven `Operation was cancelled` fatality). This fires on *both* the bg handoff and the fg reverse, and best-case background timing can't rescue it. **(b) is the only clean model.**

**Two things to get right when you build it** (both caught in verification):
1. **Build a low-level *byte-pipe* bridge, not the official app's command-level bridge.** Tesla's crypto is 100% native (Secure Enclave), so its bridge hands *CommandAction bytes* to native which then signs/seals. Copying that would move your proven, unit-tested TS sealing/framing/counter/correlation into Swift — a needless, risk-laden rewrite. Keep all command semantics in TS; native owns **only** CoreBluetooth; only the **background** passive-entry signer is native (because Hermes is dead while suspended).
2. **(b) fixes central ownership, NOT the shared counter.** The fg TS responder, the bg native signer, and the Pi path still share one car-side per-key counter (RE #8/#10). That's the *orthogonal* single-writer invariant — handled by `whoMaySign` + routable's recoverable reject, **not** by (b). Don't ship (b) thinking it makes passive entry correct.

## Q1 — which architecture does the official app use? **(b), unambiguous** (T1/T3/V1 SUPPORTED/HIGH)

The Mach-O has exactly **two** `CBCentralManager` ivars, both native, on two different-role objects:
- **`BLEVehicle._centralManager` (per-VIN) — the SOLE connection-holding central.** It implements the full lifecycle: `didConnectPeripheral:` (@0x1012b2dfc), `didDisconnect`/`didFailToConnect`, `connectPeripheral`, the `0212` write (`sendBLECommandNSData:withPeripheral:` @0x1012b7790), the `0213` notify RX (`peripheral:didUpdateValueForCharacteristic:` @0x1012b5f54), and `willRestoreState:` (@0x1012af480). Passive-entry `AuthenticationRequest`/`Response` ride this **same** central — one session multiplexes commands + challenges.
- **`BLEHelper._centralManager` — SCAN-ONLY.** `didDiscoverPeripheral:` + `startScanPeripheralsInSharedFleet`, **no** `didConnect`. It's a facade that routes `sendCommandTo:`/`sendRoutableMessage:` *down* to the per-VIN `BLEVehicle`. Its central never connects the car. (Plus a separate `EnergyBLE` central for Powerwall — a different peripheral.)

**The RN/JS layer opens no car central.** The Hermes bundle has **zero** `react-native-ble-plx`/`BleManager`/`CBCentralManager`/`connectToDevice`/`monitorCharacteristic` tokens (the only JS `*Ble` module is `EnergyBleModule`, a different peripheral). JS calls native TMBLE bridge selectors *by name* — `sendCommand`, `getTransportsList`, `scanForPeripherals`, `resetCommandPeripheral`, `clearPeripherals`, `requestMTU` — and receives CB state only as proto enums pushed up from native. Commands cross the bridge **as bytes, not a peripheral handle**. Android corroborates: `BLEModule` (RN bridge) opens no GATT; every `@ReactMethod` delegates to the singleton `BLEService`, which holds the one vehicle `Peripheral`.

> **Resolves the RESPONSE-7 restore-identifier conflict** (both prior finders were right, about different centrals): the **connection-holding** central uses the per-VIN `"%@-%@"` (`account`,`vin`) restore id (built in `BLEVehicle initWithVin:withAccount:withQueue:` @0x1012af1a0); the **scan-only** central uses the constant `"centralManagerID"` (built in `BLEHelper initializePendingLogin` @0x1012a76c0). Proven at both creation sites.

## Q2 — the fg/bg seam (moot under (b), but here's why it's clean) (T2 HIGH)

There is **no handoff window** because there's no handoff. `willRestoreState:` **re-adopts the same OS-restored central** via a setter with no new `CBCentralManager` alloc (@0x1012af480 → @0x1012af508); `restorePeripherals:` re-adopts the already-connected `CBPeripheral` from `CBCentralManagerRestoredStatePeripheralsKey` (@0x1012af648). `applicationDidEnterBackground:` does **zero** BLE teardown (@0x100008a88) — the central persists into background (that's the restore id's whole purpose). Foreground reuses the live central (creation is one-shot, cached per-VIN); a kill+relaunch restores it by identity, re-acquiring the peripheral by saved UUID (`retrievePeripheralsWithIdentifiers:` present) rather than rescanning. **The same central instance serves fg commands, fg challenges, and bg challenges across suspend/relaunch.**

## Q3 — the seam you can't see: CoreBluetooth has no cross-central handoff (V2 SUPPORTED/HIGH)

**Platform fact (Apple-documented, and the app carries no contrary API):** a `CBPeripheral` is vended by and bound to one `CBCentralManager`; `connect(_:)`/`cancelPeripheralConnection(_:)` are *central instance* methods; re-retrieving "the same" peripheral on another manager yields a **different object with no inherited live link**; State Restoration re-vends only to the central with the matching restore id. A symbol search for `transfer`/`move`/`handoff`/`migrate`/`adopt`-central returned **empty**. There is **no atomic swap**. Therefore "one central owns the peripheral for the process lifetime" is **forced**, and (a) is inherently *disconnect + fresh-connect* → the gap-XOR-overlap dichotomy above. Even the best case doesn't save (a): the background transition itself needs a fresh connect after JS drops (a gap), the foreground reverse reproduces the dichotomy, and `didEnterBackground` timing is best-effort (jetsam/OOM/forced-suspend skip it; `cancelPeripheralConnection → didDisconnect` is async). The binary even carries the matching failure tokens (`IOS_COREBTERROR_CONNECTION_TIMEOUT`, `...LEGATTNEARBACKGROUNDNOTIFICATIONLIMIT`). **(a) cannot be made clean; (b) is forced.**

## The airgapp bridge surface (byte-pipe — keep TS command semantics)

You already have the scaffolding: `modules/expo-passive-entry/ios/PassiveEntryCentral.swift` owns one restorable central (`restoreId 'airgapp.passiveentry'`) with GATT stubbed (`p.delegate=nil`), and `passiveLifecycle.ts:whoMaySign` (fg→`js`, bg→`native`). Grow it into a GATT delegate and expose a thin byte-pipe:

**Native (`PassiveEntryCentral.swift` / `PassiveEntryModule.swift`):** on `didConnect`, discover service `00000211-…`, chars `0212`(write)/`0213`(notify), `setNotifyValue(true)` on `0213`, track `maximumWriteValueLength(.withResponse)` as MTU.
- `writeFrame(frameB64) -> Promise<Void>` — write **one already-MTU-chunked** frame (TS keeps `bleFraming` chunking) to `0212` `.withResponse`; resolve on write-success.
- `connectionState() -> { state, mtu }` — so the TS transport gates its handshake and seeds `blockLength = mtu-3`.
- `setForegroundResponderActive(active)` — the `whoMaySign` gate. `true` (fg): native **forwards** every `0213` challenge up via `onFrame`, the TS responder seals it and replies via `writeFrame` (the foreground inline responder *rides the native central*). `false` (bg): native **self-signs** the `AuthenticationResponse` from the Secure-Enclave/Keychain key and does not forward.
- Events: `onFrame({ dataB64 })` — **every** `0213` notification, raw/undemuxed; `onConnectionState({ state, mtu })`.

**TS side:** a thin `BridgedBleTransport implements CarTransport` — `openSession = start(vin) + await connected`, `exchange = writeFrame(chunks) + await onFrame` (keep the `exchangeInFlight`/waiters correlator, `authResponder`, and `onUnsolicited` routing **verbatim** — it's the same three-way router `directBleTransport.ts:225-252` already runs). No `ble-plx` anywhere in it.

## airgapp changes

1. **Delete the JS-owned central** — `new BleManager()` at `directBleTransport.ts:136` and the `react-native-ble-plx` import (`:28-29`). Necessary but **not sufficient**.
2. **Kill *every* ble-plx central site — there are SIX, not one** (independently re-counted; the critic missed one). Each `new DirectBleTransport()` constructs a `BleManager` internally, so all must route through the bridge or the second central returns: `directBleTransport.ts:136`, `passiveEntryLink.ts:111`, `carlink.tsx:206` (cached command transport), `carlink.tsx:221` (BLE scan test), `carlink.tsx:262` (hedge probe), `carlink.tsx:392` (the `'ble'` selector `make()`), **and `useCarLink.ts:512`**. **Best enforced structurally: remove the `react-native-ble-plx` import from the car path entirely**, so a second phone central becomes impossible to construct.
3. **Gate the hedge probe explicitly** — `carlink.tsx:262` (`types.ts:105` "the hedge probe's second central") is the RE #10 diagnostic that *proved* the fatal contention. It must never run while `PassiveEntry.isRunning()`. Keep the dedicated link retired (`PASSIVE_ENTRY_DEDICATED_LINK=false`, `useCarLink.ts:928`).
4. **Foreground inline responder rides the native central** — `passiveEntryResponder.ts:authResponder` is invoked from the bridge's `onFrame` (not a ble-plx monitor); its sealed reply goes out via `writeFrame`. `setForegroundResponderActive(true/false)` is driven by `whoMaySign`.
5. **Pi stays a network transport, untouched** — different radio, no CoreBluetooth contention; it shares only the car-side per-key counter (serialized by `whoMaySign`, RE #10).
6. **`transportSelector.ts` needs no change** (it's pure/transport-agnostic). The rule lives in the `make()` factories: the `'ble'` candidate returns the bridge-backed transport, never a ble-plx `DirectBleTransport`. Invariant: **no JS code path opens a phone central while `PassiveEntry.isRunning()`.**
7. **Native work implied:** the module is at "connect-and-hold" — implement the CBPeripheral GATT (discover/notify/write/MTU) and the **background** `AuthenticationResponse` signer (Secure-Enclave seal while Hermes is suspended), then expose the surface above.

## ⚠ The orthogonal invariant (b) does NOT solve
Central ownership ≠ counter safety. Under (b) the **fg TS responder, the bg native signer, and the Pi path** all sign under the same enrolled key against **one** car-side per-key counter. A slip across the fg/bg edge is a counter race (RE #8/#10). This is handled separately by `whoMaySign` (exactly one signer per epoch) + routable's recoverable counter-reject — **not** by (b). The bg native signer is a *new* crypto surface that must share the same key + counter and never sign concurrently with TS.
