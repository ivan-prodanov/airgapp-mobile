# R13 §1 — The OPTIMISTIC command path, end to end

Source: iOS v4.56 `/Users/ivan/Downloads/tesla-haptics-work/main.decompiled.js` (PRIMARY, we ship iOS).
All line numbers below are iOS. Everything here is [iOS-verified] unless marked. Android UI layer not
re-checked this round (R1 established command EXECUTION is native on Android; this redux/optimistic layer
is the JS layer we RE).

## TL;DR mental model (important — corrects the "field overlay" assumption)

There is **NO field-level patch of `vehicle_data`**. The reducer stores the *whole command* as a
`CommandRecord` in `state.vehicleCommands.onGoingByVehicleId[vehicleId]` (an array). The "optimistic
display" is computed **on the fly by the display layer**, which reads the pending commands:

- **Buttons / closures** → `useClosureActionBusyStatus`/`useCommandTypeBusyStatus` → `busy = (a pending
  command whose `action` matches this control exists) && !record.finished()`. Busy → the control renders
  the `BusyIcon` spinner (R4/R10). It does **not** flip the icon to the target state — it shows the REAL
  state + spinner until the poll confirms.
- **Display text** (name / charging status) → helper selectors take `(realState, onGoingCommands)` and
  return an *effective* (optimistic) value, e.g. `getVehicleChargingStateText(chargeState, onGoing)`
  (iOS 1225331) calls an overlay helper `_closure1_slot41(chargeState, onGoing)` (1225334-1225338) that
  factors pending commands into the returned charging state, then maps to i18n text.

So "optimistic" = "keep the command in redux and let the UI derive busy/transitional display from it, then
clear it when the real state confirms OR it times out OR it fails." No boolean flip, no proto mutation.

## State shape

`state.vehicleCommands.onGoingByVehicleId` : `{ [vehicleId: string]: CommandRecord[] }`
- selector `getVehicleCommandsReduxState(state) = state.vehicleCommands` (iOS 1194499)
- selector `getAllOnGoingCommands(state) = ...onGoingByVehicleId` (iOS 1279672)
- selector `getOnGoingCommandsForVehicle(state, vehicleId) = ...onGoingByVehicleId[vehicleId]` (iOS 1279679)
- reducer key `onGoingByVehicleId` wired via combineReducers (iOS 1194497), reducer = `onGoingCommandReducer`
  fn #29049 (iOS 1187114-1194489).

`CommandRecord` class (iOS 1184568):
```
CommandRecord(commandId, action, startTime) {
  success  = false          // set true on VEHICLE_COMMAND_SUCCESS
  commandId = commandId      // uuid from caller
  action    = action         // the FULL command (CommandAction proto) — same shape sent to the car
  startTime = startTime      // Date.now() at dispatch
  // endTime added later on success
  finished() => this.endTime != null   // (iOS 1184591)
}
```
Per-vehicle array is capped at **200** records; overflow drops the last (oldest) element
(`removeLastElement`, iOS 1194471-1194483).

## 1. Dispatch

`sendVehicleOptimisticCommand(vehicleId, commandId, command, tonneauMovementStateAtBeginning)`
(iOS 1196689) → `createAction(SEND_VEHICLE_OPTIMISTIC_COMMAND, {vehicleId, commandId, command,
tonneauMovementStateAtBeginning})`. Verbatim payload keys: `vehicleId`, `commandId`, `command`,
`tonneauMovementStateAtBeginning` (iOS 1196699-1196707).

- `command` = a **CommandAction** protobuf (has `getPayloadCase()`, `getCarserverAction()`,
  `getClosureAction()`, `getRkeAction()`, `getVehicleActionMsgCase()` — see reconcile predicates). This is
  the same command object handed to the transport that talks to the car.
- `commandId` = an id string generated by the caller (used as the dedupe/find key; findIndex by
  `commandId`). Treat as a uuid.
- `tonneauMovementStateAtBeginning` = a `TonneauMovementState` enum snapshot captured at button-press
  (values seen: `OPENING`, `CLOSING`; iOS 1194367-1194376). Used ONLY for tonneau/powered-frunk toggles to
  decide direction: on dispatch the reducer synthesizes a ClosureMove action and, if the tonneau is mid-move
  (OPENING/CLOSING), rewrites the move to `CLOSURE_MOVE_TYPE_STOP` (iOS 1194402-1194410) so the optimistic
  intent is "stop" rather than a fresh open/close.

Contrast — full command:
`sendVehicleCommand(vin, vehicleId, commandId, command, source, currentRoute, ignoreForOptimistic,
hiddenCommand, transports, onSuccess, tonneauMovementStateAtBeginning)` (iOS 1196630-1196685). Same reducer
path; the optimistic variant is just the subset that always participates optimistically.

## 2. Store / "overlay" (reducer, SEND_* branch → IP 8785, iOS 1194262+)

Reducer switch dispatch (iOS 1187118-1187176): only these action types are handled (`_closure1_slot7`
whitelist): `SEND_VEHICLE_COMMAND`, `SEND_VEHICLE_OPTIMISTIC_COMMAND`, `VEHICLE_COMMAND_SUCCESS`,
`VEHICLE_COMMAND_FAILED`, `VEHICLE_PHONE_KEY_STATUS`, `VEHICLE_DATA_REQUEST_SUCCESS`. Anything else →
returns undefined (no-op).

On SEND (both types share IP 8785):
1. Read `{vehicleId, commandId, tonneauMovementStateAtBeginning, command}` from payload.
2. `ignoreForOptimistic` gate (iOS 8862/1194279): only for `SEND_VEHICLE_COMMAND` read
   `payload.ignoreForOptimistic` (null-coalesced to false). For `SEND_VEHICLE_OPTIMISTIC_COMMAND` it stays
   false. If truthy → **return state unchanged (IP 9580) — NO CommandRecord added** ⇒ no busy/overlay.
3. Tonneau special-case (iOS 8935-9384): if `command.getClosureAction().getTonneau()` is present, build a
   synthetic `CommandAction{ClosureMoveRequest}`; if tonneau OPENING/CLOSING → set move to STOP.
4. Remove any existing pending command for the **same endpoint** via `isSameEndpoint(action, newAction)`
   = `_closure1_slot17` (iOS 1184536; e.g. `CHARGEPORTDOOROPEN`/`CHARGEPORTDOORCLOSE` count as one
   endpoint, iOS 1184515-1184525) → log "Removed command for same endpoint".
5. `unshift` a new `CommandRecord(commandId, action, startTime = Date.now())` to the front of the array
   (iOS 1194446-1194459), log "onGoingCommandReducer".
6. Cap at 200 (iOS 1194471).

There is no write into `vehicle_data`/`proto_vehicle_data`. The array of pending commands IS the optimistic
state.

## 3. Reconcile / confirm (clear the overlay)

Two branches, same reconcile predicates:

A) **`VEHICLE_DATA_REQUEST_SUCCESS`** (the R1 poll — online 5000ms, offline/waking 1200ms) → IP 257
   (iOS 1187177+). Reads `payload.vehicle.proto_vehicle_data` (iOS 1187187). Builds a clear-list `r10`
   (`_closure2_slot5`), then for each optimistic field compares the REAL proto state to each pending
   command's desired state and pushes satisfied `commandId`s into the clear list. Getters used in this
   branch (counted): `getClosuresState` x9, `getVehicleState` x4, `getChargeState` x3, `getSentryModeState`,
   `getLocked`, `getChargingState`, `getIsClimateOn` (iOS 1187203-1187210 climate on/off). Predicate calls:
   `checkLockCommand` (`_closure1_slot14`), `checkChargePortCommand` (`_closure1_slot15`),
   `checkFrunkTrunkCommand` (`_closure1_slot16`, called twice = front & rear). Finally filters the array to
   drop any record whose `commandId` is in the clear-list → log "removing command". (iOS 1193994-1194032.)

B) **`VEHICLE_PHONE_KEY_STATUS`** (BLE / phone-key status) → IP 8118 (iOS 1194034+). Reads
   `payload.bleVehicleStatus.{is_connected, closure_state}`. Only reconciles when `is_connected` and
   `closure_state != null`. Then:
   - `checkLockCommand(pending, clear, closure_state.locked)` (iOS 1194057-1194059)
   - `checkChargePortCommand(pending, clear, closure_state.cp)` (iOS 1194060-1194062)
   - `checkFrunkTrunkCommand(pending, clear, /*isFront*/true, closure_state.ft)` (iOS 1194063-1194069)
   - `checkFrunkTrunkCommand(pending, clear, /*isFront*/false, closure_state.rt)` (iOS 1194070-1194074)
   - filter out cleared commandIds → log "removing BLE command".
   ⇒ **This is the offline-relevant path**: `closure_state` fields are `locked`, `cp` (charge port),
   `ft` (front trunk), `rt` (rear trunk).

The check* predicates (iOS 1186667-1186903) are exact "desired == actual" matchers:
- `checkLockCommand(cmds, clear, isLocked)`: RKE `RKE_ACTION_LOCK` records cleared when `isLocked===true`;
  `RKE_ACTION_UNLOCK` cleared when `isLocked===false`.
- `checkChargePortCommand(cmds, clear, isOpen)`: ClosureAction chargeport `CLOSURE_MOVE_TYPE_OPEN` OR RKE
  `RKE_ACTION_OPEN_CHARGE_PORT` cleared when `isOpen===true`; CLOSE / `RKE_ACTION_CLOSE_CHARGE_PORT` cleared
  when `isOpen===false`.
- `checkFrunkTrunkCommand(cmds, clear, isFront, actualState)`: reartrunk/fronttrunk `CLOSURE_MOVE_TYPE_OPEN`
  cleared when open-state matches; matched against `PHONE_KEY_CLOSURE_STATE_CLOSED` for the close case
  (iOS 1186920-1187005).

Each matched command's `commandId` is added to the clear list and removed. Cleared ⇒ busy stops ⇒ the UI
now renders the (freshly polled) REAL state.

## 4. Revert / timeout (30s)

In the SAME `VEHICLE_DATA_REQUEST_SUCCESS` handler, before the final filter (iOS 1193948-1193972):
```
now = Date.now()
timedOut = pending.filter(c => c.startTime + OPTIMISTIC_TIMEOUT_MS < now).map(c => c.commandId)
// log "timed out command(s)"
```
`OPTIMISTIC_TIMEOUT_MS = TimeInMs.THIRTY_SECONDS = 30000` (iOS 1221613-1221616; matches R1). Timed-out
commandIds are merged into the same clear-list and removed. So expiry is **evaluated on each poll tick**, not
a `setTimeout` — a stuck optimistic command is dropped on the first poll after t≥30s, and the UI snaps back
to real state (busy clears, no fake state was ever shown).

Interaction with the 7s ERROR_CARD_TIMEOUT (R1, ERROR_CARD_TIMEOUT=7000): these are **independent layers**.
The 7s error card lives in the command-lifecycle UI (R1), not in this reducer. This reducer only knows the
30s expiry. On a genuine hang (no ack, no data change): error card appears ~7s while the busy spinner keeps
running, and the optimistic record is not purged until the ≥30s poll. [7s piece = R1; cross-layer timing =
inferred from the two layers being independent.]

## 5. `ignoreForOptimistic`

- Set only on the `SEND_VEHICLE_COMMAND` payload at dispatch: `payload['ignoreForOptimistic'] = <arg>`
  (iOS 1196674). `sendVehicleOptimisticCommand` never sets it.
- Read only in the reducer's SEND branch (iOS 1194280-1194289): `x = payload.ignoreForOptimistic; use = (x
  != null) ? x : false;` and only when `action.type === SEND_VEHICLE_COMMAND` (iOS 8862). If truthy → reducer
  returns immediately (IP 9580) **without adding a CommandRecord**.
- Effect: with `ignoreForOptimistic=true`, there is NO ongoing record ⇒ `useClosureActionBusyStatus` finds
  nothing ⇒ **no busy spinner, no transitional text** for that press. (It does NOT switch to a different
  spinner; it opts the command out of the optimistic/busy system entirely — the button just relies on the
  next poll.) [The "shows a busy spinner instead" phrasing in the recon is imprecise: opting out REMOVES the
  busy behavior, it does not add one.]

## 6. Explicit failure vs success (VEHICLE_COMMAND_* → IP 8375, iOS 1194111+)

Find the record by `commandId` (findIndex). If not found → log "command not found", no-op.
Then gate on `commandCausesVehicleDataUpdate(command)` = `_closure1_slot13` (iOS 1185153, 1194158):
- **command does NOT cause a vehicle-data update** (fire-and-forget) → splice the record out **immediately**
  on ack, success or fail alike → log "f&f command removed" (iOS 1194162-1194176). No waiting for a poll.
- **command DOES cause a vehicle-data update**:
  - `VEHICLE_COMMAND_FAILED` (iOS 1194186 `type !== VEHICLE_COMMAND_SUCCESS` path, IP 8634): filter out this
    command **and every same-endpoint command** (`isSameEndpoint`, `_closure1_slot17`) → logs "removing
    same-endpoint command on failure" + "command failed" (iOS 1194188-1194236). ⇒ **on explicit failure the
    optimistic overlay reverts immediately** (busy clears, UI shows real state at once — no 30s wait).
  - `VEHICLE_COMMAND_SUCCESS` (IP 8701, iOS 1194238-1194257): set `record.endTime = Date.now()`,
    `record.success = true`, KEEP the record → log "command success". `finished()` now true ⇒ `busy` clears,
    but the record persists so the subsequent `VEHICLE_DATA_REQUEST_SUCCESS`/BLE reconcile can confirm the
    real field changed and then remove it (or the 30s expiry sweeps it). i.e. command-level success stops the
    spinner; data-level reconcile does the final cleanup.

## EXACT TIMELINE (single optimistic closure command, e.g. open frunk)

- t=0: press → `sendVehicleOptimisticCommand(...)` → `SEND_VEHICLE_OPTIMISTIC_COMMAND` →
  `CommandRecord{startTime:0, endTime:null, success:false}` unshifted → `busy=true` → BusyIcon spinner.
- t≈0–5s: poll cadence 1200ms (waking/BLE) or 5000ms (online). First `VEHICLE_DATA_REQUEST_SUCCESS` or
  `VEHICLE_PHONE_KEY_STATUS` whose real state (frunk open) matches → `checkFrunkTrunkCommand` clears the
  record → spinner stops, real "open" state shown. **Happy path ends here.**
- If a `VEHICLE_COMMAND_SUCCESS` arrives first: endTime set, success=true → spinner stops (busy=false) even
  before the data poll; record removed by the next reconcile/expiry.
- If `VEHICLE_COMMAND_FAILED`: record (+ same-endpoint) removed immediately → spinner stops, reverts to real
  state at once. Separately, R1's failure card ("<Command> failed" / "Command timeout, please try again.")
  handles the visible error toast.
- t≈7s (hang only): R1 ERROR_CARD_TIMEOUT shows the error card; optimistic record still pending, spinner
  still running.
- t≥30s (hang only): first poll after startTime+30000<now → record swept as "timed out command" → spinner
  stops, snaps to real state.
